Mac AI 专线防护

给 Claude 桌面版 和 Google Antigravity 单独搭的一条“台湾专线”。它要做到三件事：

只走台湾出口，不会悄悄换成别的国家
节点不乱跳，选定一个稳的就一直用
出事就停，宁可断网也不裸连、不泄露真实地址
01 · 整体结构

一条数据怎么走

电脑上同时有两条路。被保护的两个 App 走上面那条专线；其他程序（浏览器、Codex 等）照常走代理客户端的普通路线。DNS 守护在旁边盯着，发现 DNS 出问题就先把两个 App 锁住。

手机上可以左右滑动看图。

02 · 每一层

各部分分别做什么

底座代理客户端 TUN

用的是基于 mihomo 内核的客户端，开 TUN 模式，全机流量和 DNS 都被它接管。DNS 只用国外的加密 DNS，不用国内 DNS。

它用的是 “fake-ip” 模式：程序问域名时先拿到一个假地址（198.18.x.x）。这对普通程序没问题，但会坑到下面的专线：专线是另一个独立的 mihomo，看不懂这些假地址，就连不上。

解决办法：把 Claude、谷歌、GitHub 的域名加进客户端的 fake-ip-filter（假地址白名单），让这些域名拿到真实地址。比如 +.claude.ai、+.anthropic.com、+.googleapis.com、+.gstatic.com、+.github.com。

分流ProxyBridge

一个能按“程序名”强制转发流量的小工具。配置里写了 4 条规则：

  • Claude TCP → 本地台湾专线的端口
  • Claude UDP → 直接拦截
  • Antigravity TCP → 本地台湾专线
  • Antigravity UDP → 直接拦截

拦 UDP 是为了堵住 QUIC、WebRTC 这类可能绕开代理的通道。它用 LaunchAgent 开机自动启动，挂了会被拉起来。

核心本地台湾专线

自己写的一个 Python 脚本，在本机再起一个 mihomo，里面只放台湾节点。规则是“稳字当头”：

  • 给每个节点打分，记一个 0–100 的“信任分”。
  • 选定一个就粘住不放，不会因为别的节点快一点就换。只有当前这个真的坏了才换下一个最稳的。
  • 每 5 秒体检一次：出口是不是台湾、Claude 能不能连上。
  • 每 30 秒查一次谷歌（给 Antigravity 用）。连续 3 次连不上，就拿备用节点试；备用能连才换。如果所有节点都连不上谷歌，说明是谷歌自己的问题，不乱换。
  • 出过问题的节点进“黑名单”1 小时，期间不用它。
  • 状态写进一个 JSON 文件，面板和弹窗都读这个文件，所以三处显示的是同一个结论。
兜底DNS 守护

后台常驻的脚本，只检查系统当前用的 DNS 服务器是不是可信的那几个。

如果客户端崩了、DNS 掉回系统默认，它会先锁住两个 App（把程序文件设为不可打开，并结束正在运行的进程），然后才启用应急 DNS。等一切恢复正常，自动解锁。先锁再动，保证这段时间两个 App 不会用错误的网络连出去。

03 · 意外情况

出了事会怎样

自动处理，无感还能用，但会提醒主动断开，保护优先

当前台湾节点卡了或掉线

程序换到下一个最稳的台湾节点，坏节点拉黑 1 小时。
你看到面板上节点名字变了，别的不用管。

某个节点出口突然不是台湾了

程序体检发现国家不对，立刻拉黑并换掉。
你看到同上，面板会写明换掉的原因。

节点能连 Claude，但连不上谷歌

程序连续 3 次失败后对比备用节点；备用能连谷歌才换。谷歌整体挂了就不动。
你看到面板提示“刚才连不上谷歌”。

ProxyBridge 停了

程序两个 App 改走客户端的普通路线：仍然在代理里，但不保证是台湾。
你看到弹窗和面板会提示“专用保护没开”，用安全启动打开时会拦住。

所有台湾节点都不能用

程序专线没有出口，两个 App 连不上网，不会改走其他国家。
你看到持续 45 秒以上才弹窗（避免一闪而过的误报），恢复后再弹一次“专线好了”。

代理客户端崩溃，DNS 掉回系统默认

程序DNS 守护先锁住两个 App 并结束进程，再启用应急 DNS；恢复后自动解锁。
你看到弹窗“已锁定”；这段时间 App 打不开，属于正常保护。
04 · 小工具

看得见的部分

后台跑的东西看不见，所以做了三个 SwiftUI 小程序，都读同一份状态文件。

AI 网络状态

一个面板，一句话总结现在能不能放心用，下面列出 DNS、启动锁、ProxyBridge、当前台湾节点和信任分。

开启提醒

常驻后台的弹窗。只有三种状态：正常、已锁定、专线断了。断线要持续 45 秒才提醒。

安全打开

启动器，Claude 和 Antigravity 各一个。打开前逐项检查 DNS、断网保护、专线节点，Antigravity 多查一项谷歌。全部通过才打开 App，有一项不过就不打开并说明原因。

05 · 取舍

目前没管到的地方

  • 只保护这两个桌面 App。浏览器、Codex 等走客户端的普通路线，仍有客户端的 TUN 和 DNS 保护，只是不锁定台湾。这是有意的选择，管得越多越容易出问题。
  • Antigravity 走专线时，只能打开谷歌和 GitHub 相关的网站。别的网站拿到的是假地址，专线连不上。要用别的网站，得把域名加进假地址白名单。
  • Antigravity 附带的命令行工具没有被单独保护。
  • 没有改系统防火墙（pf）这类系统级设置。万一 ProxyBridge 停了，靠的是提醒和启动检查，不是硬拦截。
06 · 自己搭一套

大致步骤

  1. 先把底座弄好

    代理客户端开 TUN，DNS 换成国外加密 DNS，确认没有国内 DNS。

  2. 加假地址白名单

    把要保护的 App 会用到的域名写进 fake-ip-filter。改完重启客户端。

  3. 起一个只有台湾节点的本地 mihomo

    写个脚本定时体检：出口国家、目标网站能否连通。按“稳定优先、坏了才换、坏的拉黑一段时间”的思路选节点，把结果写进状态文件。

  4. 按程序分流

    装 ProxyBridge，规则写成目标 App 的 TCP 走本地专线端口、UDP 拦截，用 LaunchAgent 开机自启。

  5. 加 DNS 兜底

    后台脚本盯着系统 DNS，出问题时先锁住 App，再切应急 DNS，恢复后解锁。

  6. 做提醒和启动器

    可选，但很有用。都读同一个状态文件，避免几个地方说法不一。

  7. 逐个故障演练

    查出口 IP；手动让一个节点失效，看会不会换；关掉 ProxyBridge，看提醒和启动器会不会拦住。

几条底线

  • 任何时候都不用国内 DNS。唯一例外是应急 DNS，而且启用前必须先锁住 App。
  • 改任何配置前先备份旧文件，改坏了能直接换回去。
  • 改重要脚本时留一个“几分钟后自动还原”的保险，确认新版正常再取消。
  • 出问题时宁可断网，也不要让 App 自动换到别的路线。
